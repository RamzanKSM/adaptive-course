# Rmzn Tutor backend (Java и Python)

Локальный MVP: Java 21, Spring Boot, SQLite, Flyway и JDBC. Запускать из этой папки:

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) mvn package
java -jar target/adaptive-java-tutor-0.1.0.jar
```

## Локальный Docker запуск

Из папки `adaptive_course`:

```sh
cp .env.example .env
# задать непустой APP_BOOTSTRAP_ADMIN_PASSWORD в .env до запуска
docker compose up --build -d
```

Интерфейс будет доступен только с этого компьютера на `http://127.0.0.1:8080`. Compose не публикует Piston наружу: backend обращается к нему по внутреннему адресу `http://piston:2000`. `adaptive-data` хранит SQLite, а `codex-home` — авторизацию Codex и persistent rollout data; оба named volume переживают пересоздание backend container.

## Развёртывание на VPS

Compose намеренно публикует backend только на `127.0.0.1:8080`. На VPS перед ним нужен HTTPS reverse proxy, который принимает внешний трафик и проксирует его на этот loopback-адрес. Есть reviewable [фрагмент Caddyfile для `course.rmzn.net`](../deploy/Caddyfile.course): добавьте только этот фрагмент в существующий Caddyfile, не заменяя конфигурации других хостов. В рабочем `.env` задайте уникальный `APP_BOOTSTRAP_ADMIN_PASSWORD` и `APP_COOKIE_SECURE=true`: иначе защищённая cookie не будет передаваться браузером по HTTPS. `.env`, `codex-home`, SQLite и ключи сертификатов не добавляются в Git.

Для Codex `bwrap` backend использует [узкий custom seccomp profile](../deploy/seccomp/backend-bwrap.json). Его baseline — точный [Docker/Moby default profile `docker-v29.6.1`](https://raw.githubusercontent.com/moby/moby/docker-v29.6.1/vendor/github.com/moby/profiles/seccomp/default.json), сохранённый без изменений вне двух добавленных правил. Добавлены только `unshare`, `mount`, `umount2`, `pivot_root` и `clone` при флаге `CLONE_NEWUSER`; `seccomp=unconfined` не используется. На этом VPS нет AppArmor/SELinux, поэтому нельзя приписывать baseline отдельную защиту `socketcall` или AF_ALG: Docker 29.4.3 перенёс её на LSM. Это расширяет syscall surface backend container и требует одноразовой проверки bwrap на VPS. Если bwrap запросит другой syscall, его нужно подтвердить по deny log и добавить отдельно, не ослабляя профиль целиком.

Piston остаётся без опубликованного порта и запускается privileged, поэтому его нельзя открывать напрямую в интернет. LLM остаётся выключенной и fail-closed по умолчанию. На `course.rmzn.net` она включена только явными переменными `.env` после проверки sandbox; это opt-in конфигурация развёртывания, а не изменение безопасных дефолтов образа.

Для VPS с 4 GB RAM Compose ограничивает backend до 768 MB, Piston до 2 GB и оставляет память ОС и reverse proxy. Piston одновременно запускает не больше двух jobs. Лимиты одного запуска Java заданы отдельно: 256 MB на компиляцию и 128 MB на выполнение. Образ Piston зафиксирован официальным immutable digest, а не подвижным `latest`; обновление образа требует отдельной проверки и изменения Compose. Перед сборкой или обновлением проверьте свободное место командой `df -h /`, Docker cache и volumes — через `docker system df`, а заполнение логов — отдельно; очистка cache или данных выполняется только отдельной осознанной операцией.

Piston запускается пустым: Java runtime нужно поставить один раз после запуска, затем проверить, что он виден API. Runtime хранится в named volume `piston-packages`. Образ API не содержит package-manager CLI, поэтому для установки нужен checkout официального Piston repository и временный Node-контейнер в той же Compose-сети:

```sh
git clone --depth 1 https://github.com/engineer-man/piston.git .piston-cli
docker run --rm --network adaptive-course_default \
  -v "$PWD/.piston-cli/cli:/cli" -w /cli node:22-bookworm \
  sh -lc 'npm ci && node index.js -u http://piston:2000 ppman install java'
docker run --rm --network adaptive-course_default \
  -v "$PWD/.piston-cli/cli:/cli" -w /cli node:22-bookworm \
  sh -lc 'node index.js -u http://piston:2000 ppman list | grep "^java"'
```

Только после второй команды отправка Java-решения сможет пройти Piston.

Для курса Python так же один раз установите Python runtime (рекомендуется 3.12) и проверьте его:

```sh
docker run --rm --network adaptive-course_default \
  -v "$PWD/.piston-cli/cli:/cli" -w /cli node:22-bookworm \
  sh -lc 'node index.js -u http://piston:2000 ppman install python=3.12.0'
docker run --rm --network adaptive-course_default \
  -v "$PWD/.piston-cli/cli:/cli" -w /cli node:22-bookworm \
  sh -lc 'node index.js -u http://piston:2000 ppman list | grep "^python"'
```

Если установлено несколько версий Python, backend берёт самую новую; конкретную можно закрепить переменной `PISTON_PYTHON_VERSION`. Пока Python runtime не установлен, курс Python работает, но проверка решений возвращает «проверка недоступна» (`PISTON_PYTHON_NOT_INSTALLED`), а генерация новых задач Python не запускается. `.piston-cli` — локальная служебная папка, её можно удалить после установки. API runtimes можно проверить из backend network запросом `GET http://piston:2000/api/v2/runtimes`. Инструкция основана на [официальном Piston README](https://github.com/engineer-man/piston).

На текущем официальном каталоге после установки доступен `java` версии `15.0.2`; это отдельный runtime Piston, а не Java 21, на которой работает backend. Поэтому задачи должны быть совместимы с Java 15 и не использовать синтаксис или API, появившиеся только в Java 16–21.

Codex CLI запускают отдельным одноразовым контейнером с **тем же** `codex-home` volume и тем же user, что у backend:

```sh
docker compose run --rm --no-deps backend codex logout
docker compose run --rm --no-deps backend codex login --device-auth
docker compose run --rm --no-deps backend codex login status
```

Для смены аккаунта сначала остановите backend: `docker compose stop backend`. Затем выполните три команды выше в указанном порядке: logout, device auth под новым ChatGPT/Codex-аккаунтом и status. После этого измените в `.env` на новое непустое значение `CODEX_ACCOUNT_NAMESPACE`, затем запустите backend. Старые remote thread ID могут быть недоступны новому аккаунту; локальная история уроков и чата в SQLite сохранится. Не печатайте и не копируйте `auth.json`; volume `codex-home` не попадает в Git.

При первом запуске задайте `APP_BOOTSTRAP_ADMIN_LOGIN` и `APP_BOOTSTRAP_ADMIN_PASSWORD`. Backend создаст единственного первого администратора с bcrypt-хешем пароля. Если в базе уже есть администратор, эти переменные игнорируются. Дефолтной учётной записи и пароля нет.

Чтобы начать локальный MVP с чистой базы и применить новые bootstrap-данные, остановите Compose и удалите только его named volumes:

```sh
docker compose down --volumes
docker compose up --build -d
```

Команда удаляет SQLite, `codex-home` и установленные Piston runtimes этого проекта; она не предназначена для уже нужных пользовательских данных.

### Качество задач

Каждая сгенерированная задача описывает свою учебную цель (`goal` в `tasks.goal_json`):

- `FIXED_ARITHMETIC` — посчитать фиксированный результат одним действием над числами из условия (например, 4 билета по 6: `*` над `[4, 6]`, вывод `24\n`). Вычисление засчитывается, если напечатанное значение получено из него: прямо в `println`/`print`, через переменные (`int cost = 4 * 6; println(cost)`) или через собственный метод студента, в том числе с параметрами (`cost(6, 4)` с `return price * count`). Числа могут быть литералами, неизменными переменными или аргументами вызова; переменные сопоставляются по имени. Числа из условия, данные текстом, тоже считаются: `int("14")`, `float(price)`, `Integer.parseInt(count)`, `Double.parseDouble(text)` дают число из строки, а склейка строк (`"14" + "6"`) — нет;
- `FUNCTION_BEHAVIOR` — функция проверяется результатами на нескольких разных входах, реализация свободная;
- `OUTPUT_TEXT` — точный текст;
- `CONSTRUCT` и `requiredConstructs` — условие явно требует конструкцию (цикл, присваивание, блок `finally` и т. п.). «Список (массив)» в Java — массив или `List`/`ArrayList`/`LinkedList`; параметр `String[] args` у `main` есть в любой программе и не считается.

Задача сохраняется, только если эталонное решение проходит проверки, а все неверные решения — присланные генератором и созданные сервером (готовый ответ `print(24)`, другие числа `print(12 * 2)`, верное действие с неверным выводом, лишний/пропущенный перевод строки) — запускаются и проваливают именно проверку, а не падают. Иначе генерация повторяется (до 3 раз). Структура кода проверяется только там, где этого требует цель: для Python — разбором AST в момент проверки (операнды могут быть числами или переменными с числовым значением), для Java — деревом компилятора JDK на backend до запуска в Piston. Поэтому runtime-образ backend собран на JDK, а не на JRE.

Задачи, принятые прежней проверкой только по выводу (`quality_version` ниже текущей), фоновая задача `TaskAudit` перепроверяет при старте и каждые 15 минут, пока доступны LLM и Piston: условие остаётся прежним, проверки заменяются проверенными; если надёжные проверки получить не удалось, задача снимается и будет сгенерирована новая. Уже записанные результаты отправок, зачёты и прогресс не пересчитываются. Отключить: `APP_TASK_AUDIT_ENABLED=false`.

Модели, уровни размышлений, ограничения и логирование LLM меняются в админке («Настройки LLM») и хранятся в `app_settings`; изменения применяются к следующим обращениям без перезапуска. Для каждого вида работы — своя модель и свой уровень: ответы помощника в чате (`CHAT`), генерация и перепроверка задач (`TASK`, перепроверка `TASK_REPAIR` использует те же настройки), объяснения тем (`EXPLANATION`). Модель и уровень передаются в каждый `turn/start`, поэтому смена действует и в уже начатых чатах студентов. Список моделей и их уровни берутся из `model/list` App Server. Дополнительно всегда предлагаются модели из `APP_LLM_EXTRA_MODELS` (через запятую, по умолчанию `gpt-5.6-terra`): если App Server их не перечислил, они помечены «не подтверждена» и получают базовые уровни `low`/`medium`/`high` — проверьте, что аккаунт Codex имеет к ним доступ. Уровень проверяется по модели своего вида работы. Переменные окружения задают значения по умолчанию, пока их не изменили в админке: модели — `CODEX_MODEL_CHAT`, `CODEX_MODEL_TASK`, `CODEX_MODEL_EXPLANATION` (пустые — используется `CODEX_MODEL`); уровни — `CODEX_REASONING_EFFORT_TASK=high`, `CODEX_REASONING_EFFORT_CHAT=low`, `CODEX_REASONING_EFFORT_EXPLANATION=medium`, `CODEX_REASONING_EFFORT` — для незаданных. В «Аналитике LLM» у каждого вида работы видна модель последнего вызова.

Ограничения независимы друг от друга (0 — без ограничения), считаются по `llm_calls` в скользящих окнах и переживают перезапуск:

- сообщений помощнику на студента в час и в сутки (`APP_LLM_CHAT_PER_HOUR=30`, `APP_LLM_CHAT_PER_DAY=150`) — сверх лимита `POST /api/chat` отвечает `429 LLM_RATE_LIMITED` с `Retry-After`, вопрос не сохраняется;
- генераций задач в час на весь курс (`APP_LLM_TASKS_PER_HOUR=100`: новые задачи и перепроверка старых) — сверх лимита генерация пропускается так же, как при недоступной LLM: берётся ближайшая задача из банка, иначе урок сообщает `LLM_RATE_LIMITED`;
- генераций объяснений тем в час на весь курс (`APP_LLM_EXPLANATIONS_PER_HOUR=30`) — сверх лимита урок идёт без объяснения, пока лимит не освободится.

### Банк готовых задач (Python и Java)

Для тем, где генерация не справлялась или задач не было, в рабочую базу залиты задачи, написанные вручную (`source='CURATED'`, ключ `curated:<семейство>:<номер>`): по всем темам Python и по Java-темам начиная с `if/else`. Каждое семейство — одна формулировка с тремя наборами значений, по семейству на сложность. Студент пишет вычисление по готовым данным; проверка запускает программу как есть и затем с другими значениями данных, поэтому напечатанный готовый ответ не проходит.

Выбор задачи учитывает семейства, чтобы на повторе не попадалась «та же задача с другими числами». Семейство решено, если студенту засчитан любой его вариант; задача не из банка (LLM, seed) — семейство сама по себе. Порядок задач темы (`availableTasks`): сначала задачи нерешённых семейств, затем как раньше — нужная сложность, ближайшая, без сложности последними; семейства — в порядке банка, а варианты одного семейства — в своём порядке для каждого студента (перестановка id, зависящая от id студента: соседи по парте получают разные первые варианты, один студент — всегда тот же). Нерешённое семейство идёт раньше варианта решённого даже на другой сложности. Если задачи нужной сложности из нерешённого семейства нет, задача генерируется (как при отсутствии задачи нужной сложности); если генерация невозможна или не удалась, выдаётся первая по этому порядку — в крайнем случае другой вариант решённого семейства (в логе: `another variant of the solved story`). Hard mode это не затрагивает.

- Python: данные — переменные в начале заготовки (`a = "14"`); проверка подставляет другие значения в эти строки и запускает программу снова.
- Java: данные — статические поля класса `Solution` (`static String count = "4";`); проверка через рефлексию записывает в поля другие значения и снова вызывает `main`, восстанавливая перед каждым прогоном значения полей и названное в задаче статическое состояние. То, чего не видно по синтаксическому дереву (интерфейс, `private`-поле, метод бросает исключение), проверяется по поведению или рефлексией; `switch` и выбранная коллекция (`LinkedHashSet`, `Map`, `TreeSet`…) — по байткоду класса `Solution` (инструкции `tableswitch`/`lookupswitch`, имена классов в пуле констант). Если байткод прочитать не удалось, проверка решение не отклоняет.
- Задачи на методы и функции проверяются по возвращаемым значениям, как сгенерированные.

Инструмент — [`tools/curated_python/`](../tools/curated_python): темы описаны файлами `topics/tNN_*.py` (Python) и `topics_java/tNN_*.py` (Java); `build.py` собирает задачи и проверяет их локально (Java — `javac --release 15`), `Verify.java` прогоняет каждую через `TaskVerifier.verify` на настоящем Piston (как сгенерированную задачу), `import_bank.py` записывает проверенные задачи в базу одной транзакцией. Повторный импорт обновляет задачи по ключу, не создавая дублей; отправки и зачёты остаются привязаны. Фоновая перепроверка (`TaskAudit`) такие задачи не трогает.

### Группы студентов

У студента может быть группа (`users.group_name`, необязательно). Отдельного справочника нет: группа существует, пока в ней есть студенты. Название сохраняется без лишних пробелов; если оно отличается от существующей группы только регистром или пробелами, студент попадает в неё («ивт-1» → «ИВТ-1»).

- Список студентов и таблица «Студенты» в «Аналитике LLM» фильтруются по группе («Все», группы, «Без группы»); выбор запоминается в браузере. При выборе группы она подставляется в форму новой учётной записи.
- `PATCH /api/admin/students/{id}` с `{login?, displayName?, group?, sessionParticipant?}` меняет только переданные поля; пустая группа убирает её (участие в сессии — см. «Аналитика прогресса»). Новый логин действует со следующего входа, открытые сессии и пароль не меняются. Изменения пишутся в лог с прежними значениями.
- `POST /api/admin/groups/rename` с `{from, to}` переименовывает группу у всех её студентов; название существующей группы объединяет их, пустое — убирает группу.

### Консоль: что напечатала программа

Скрытые проверки перехватывают вывод решения, поэтому студенту дополнительно показывается обычный запуск программы, без проверок: Java — `Solution.main`, Python — `solution.py` как скрипт. В нём нет ничего скрытого, поэтому студент видит всё: вывод с отметками переводов строк (↵) и пробелов в конце строк, ошибки компиляции и выполнения с номерами своих строк, срабатывание лимитов.

- Кнопка «Запустить» (`POST /api/run?language=…`) только запускает код: это не отправка, попытка не создаётся, на зачёт и прогресс не влияет. Не больше 30 запусков в минуту на студента, сверх — `429 RUN_RATE_LIMITED` с `Retry-After`.
- «Отправить на проверку» делает такой же запуск параллельно с проверкой (два задания Piston одновременно) и сохраняет вывод в `submissions.console_json`: студент видит его под результатом, преподаватель — в истории урока.
- Помощник получает в контексте вывод последней проверки и консоль, которую студент видит на экране.
- Ввод с клавиатуры пустой; Java-задача без `main` не запускается (проверка сама вызывает методы). Вывод ограничен 200 строками и 10 000 символами; в compose Piston разрешает до 20 000 символов на поток (`PISTON_OUTPUT_MAX_SIZE`, по умолчанию у Piston 1024).

### Как проверяются решения

Способ проверки зависит от типа задачи (`goal.kind`):

| Тип | Результат | Подход |
|---|---|---|
| `OUTPUT_TEXT` — вывод текста | запуск, сравнение вывода | — |
| `FIXED_ARITHMETIC` — «посчитай» | запуск, сравнение вывода | LLM (`REVIEW`): посчитан ли ответ из чисел условия; если LLM недоступна или исчерпан лимит `APP_LLM_REVIEWS_PER_HOUR` — синтаксическое дерево |
| `CONSTRUCT` — «используй цикл…» | запуск | синтаксическое дерево: есть ли конструкция |
| `FUNCTION_BEHAVIOR`, `IO_BEHAVIOR` — функции и hard | тест-кейсы платформы | — |

- **Тест-кейсы** (`task_cases`). Генератор даёт только входные данные (`testInputs`: аргументы вызова или ввод) и эталонное решение. Ответы записывает платформа, запуская эталон в Piston; код проверки собирается по шаблону (`TestCases`). В каждой проверке — все примеры из условия и до 8 случайных скрытых кейсов. Задача отклоняется, если эталон падает на каком-то входе, у всех входов один ответ или неверные решения проходят кейсы.
- **Объяснение отказа.** Неверный пример: «ожидалось / получилось». Скрытый кейс: только «Тест N из M не пройден», без данных. Неверный вывод в задачах без скрытых кейсов: вывод программы рядом с нужным (↵ — перевод строки, · — пробел в конце). Нет конструкции: что требует условие, чего нет и почему это важно. Готовый ответ в «посчитай»: строка и подсказка от LLM. Проверяющий не заменяет помощника — подробный разбор в чате.
- Проверки на Java запускаются через `PlatformLauncher`, который переключает вывод и ошибки в UTF-8: Piston запускает Java в однофайловом режиме с не-UTF-8 кодировкой, и без этого русские сообщения приходили бы знаками вопроса.
- Старые задачи на функции без записанных кейсов фоновая задача `TaskAudit` постепенно переводит на тест-кейсы.

### Hard mode

Преподаватель выдаёт студенту допуск (карточка студента → «Hard»), студент включает режим сам — переключатель в шапке. Режим открывается в курсе только после первого прохода: по каждой теме курса есть хотя бы одна завершённая итерация, или тема освоена, или подтверждена диагностикой. Готовность считается отдельно для Java и Python (`hardModeCourses` в профиле студента); пока курс не пройден, переключатель закрыт замком и подсказывает, сколько тем осталось, а включённый ранее режим в этом курсе не действует. Помощника для студентов в hard mode можно отключить отдельно: «Настройки LLM → Помощник в hard mode» (`APP_HARD_MODE_CHAT=true` по умолчанию); генерация задач от этого не зависит. В hard mode — отдельная дорожка, не связанная с темами и повторами: урок выдаёт следующую нерешённую задачу банка hard-задач (в порядке курса, от лёгких к сложным), даже если по графику подошёл повтор какой-то темы; повторы идут в обычном режиме. Задачи алгоритмические: программа читает данные со стандартного ввода (чтение уже написано в заготовке), проверяют её тест-кейсы платформы (см. выше), а платформа добавляет свою ловушку — вывод ответа из примера при любом вводе (цель `IO_BEHAVIOR`). Банк — задачи по мотивам [Exercism problem-specifications](https://github.com/exercism/problem-specifications) (MIT): 26 задач, 51 вариант на Java и Python, тест-кейсы — из эталонных данных Exercism (см. `src/main/resources/hard-tasks/README.md`). Hard-задачи не генерируются: сгенерированным алгоритмическим задачам преподаватель не доверяет, прежние сгенерированные отключены (`V25`). Когда банк курса решён, урок отвечает `reason=HARD_BANK_COMPLETE`. Задачи хранятся отдельно (`tasks.mode='HARD'`); решённая задача засчитывается и её теме, как обычная; за каждую — 30 XP вместо 10 и отдельные достижения. Обычные задачи с вводом отклоняются: обычные студенты чтение ввода не проходили. Для hard-задач у «Запустить» есть поле «Входные данные». Переключатель режима срабатывает сразу, даже пока для урока готовится задача: подготовка перед выдачей проверяет режим, а задача старого режима уходит в очередь.

### Завершение урока

Урок завершает студент («Завершить урок»), админ или выход из аккаунта: `POST /api/auth/logout` студента завершает его открытые уроки во всех курсах. Завершить урок можно в любой момент, в том числе пока готовятся объяснение или задача, — завершение не ждёт генерацию. Начатая генерация доводится до конца и не теряется: объяснение сохраняется для темы, а задача — в банк и в очередь студента (`pending_redos` с `reason='GENERATED'`), поэтому следующий урок этого курса начнётся с неё. Новые попытки генерации для завершённого урока не запускаются; `/api/learning/next` такого урока отвечает `reason=LESSON_FINISHED`, а интерфейс игнорирует ответ запроса, который студент уже покинул.

### Диагностика по темам

Результат диагностики сохраняется по каждой теме (`diagnostic_skill_results`). Тема считается подтверждённой, если на все её вопросы дан верный ответ; если вопрос по теме один — дополнительно нужно не меньше 80% верных ответов в его блоке (один верный ответ из четырёх вариантов может быть угадан). Ошибка или «Не знаю» хотя бы в одном вопросе темы — тема требует практики.

Подтверждённые темы пропускаются: практика назначается только по неосвоенным и неподтверждённым темам в порядке курса, без привязки к стартовому блоку. Если все темы подтверждены или освоены, урок сообщает `COURSE_COMPLETE`, а не начинает последний блок. Подтверждение не создаёт итераций, зачётов задач и освоения — в интерфейсе оно показано отдельно. Для студентов, прошедших диагностику раньше, результаты по темам вычисляются из сохранённых ответов при старте. Тема закрепляется за три итерации (3, 2 и 1 задача за урок): первая — в любом уроке N, вторая — в уроке N+1 или позже, третья — в уроке N+3 или позже (номера уроков свои для каждого курса). Пропущенный повтор не теряется: тема остаётся «пора повторить», пока его не сделают (`IterationRule`). За урок засчитывается не больше одной итерации темы, поэтому после засчитанной итерации урок переходит к другой теме, даже если по расписанию пора и следующая (так бывает после просроченного второго повтора): она ждёт следующего урока.

### Аналитика прогресса и прогноз к сессии

Вкладка «Прогресс» у преподавателя (`GET /api/admin/progress?language=&from=&to=`), экран для группы (`GET /api/admin/classroom?language=&group=`) и блок `session` в `GET /api/progress` студента. Для неё ничего не хранится отдельно (`ProgressAnalytics`): история восстанавливается из уже существующих данных, курс читается фиксированным числом запросов и считается в памяти. Все дни — дни UTC.

- **История.** Задача засчитана с момента своей первой принятой и не отменённой отправки. Итерации проигрываются урок за уроком тем же правилом, что и при зачёте (`IterationRule`: его используют и `credit()`, и пересчёт после отмены решения), каждая задача — в момент её первой принятой отправки в уроке. Подтверждения диагностики действуют с `student_languages.diagnostic_completed_at`. Поэтому последний день графиков совпадает с тем, что видит студент, а отменённое решение исчезает и из истории.
- **Доля темы** (0..1) — как полоска темы у студента: 1, если тема освоена, иначе (задачи завершённых итераций + засчитанные задачи текущей, но не больше её размера) / 6.
- **Навыки, %** — 100 × сумма долей / число тем курса. Вариант **с диагностикой** считает подтверждённую и не освоенную тему за 1, начиная с даты диагностики.
- **Решено задач** — засчитанные сейчас задачи курса по дате первой принятой отправки. **Опыт (XP)** — ровно формула `experience()` из `frontend/src/game.ts`.
- **Тема пройдена к сессии** — есть хотя бы одна итерация (или тема освоена) либо её подтвердила диагностика (с даты диагностики). Линия `closed` у преподавателя и `closedSeries` у студента — число таких тем на конец каждого дня.
- **Темп** — темы, у которых первая итерация практикой завершена за последние 21 день, делённые на `min(3, max(1, недель с первого урока курса))` — тем в неделю. Подтверждения диагностики в темп не входят. **Нужный темп** — оставшиеся темы / недели до сессии.
- **Статус**: тем не осталось — `DONE`; без даты сессии статуса нет; недель до сессии не осталось — `BEHIND`; темп не ниже нужного — `ON_TRACK`; не ниже 75% нужного — `BORDERLINE`; иначе `BEHIND`. **Прогноз окончания** — сегодня + оставшиеся / темп × 7 дней (при нулевом темпе прогноза нет). Прогноз считается на текущий момент, а не на конец выбранного периода.
- **Курс сессии студента** — курс, где у него больше уроков (при равенстве — с более поздним уроком); без уроков — курс диагностики (последней из двух).
- **Участник сессии** (`users.session_participant`, по умолчанию да). Преподаватель снимает флаг себе, вольнослушателям и тестовым учётным записям: `PATCH /api/admin/students/{id}` с `sessionParticipant`, изменение пишется в лог; флаг виден в `GET /api/admin/students` и карточке студента. Групповые итоги, экран группы, прогноз и флаги учитывают только **членов курса** — участников, для которых это курс сессии. Остальные видны преподавателю в списке с `member: false`, без прогноза и флагов.
- **Флаги** (только преподавателю): `NOT_STARTED` — нет уроков в курсе; `GONE` — последняя активность (начало урока, отправка, сообщение помощнику) 7 и более дней назад; `STUCK` — в открытом уроке последняя задача не принята 5 раз подряд; `BEHIND` / `BORDERLINE` — по статусу.
- **Дата сессии** одна на платформу: `GET/PUT /api/admin/session` с `{"date": "ГГГГ-ММ-ДД"}` или `{"date": null}` (удаляет), хранится в `app_settings.session_date`.
- Период преподавателя по умолчанию — последние 30 дней. Линии в ответе всегда начинаются с первого урока курса (история целиком): страница сама показывает выбранный период, считает прирост от дня перед ним и выравнивает студентов по их первому уроку; период ограничивает только цифры за период.

Видимость согласована с преподавателем:

- **Экран группы** проецируется на всю группу, поэтому в нём только анонимные итоги по её членам: закрыто тем за текущую неделю (с понедельника) и цель недели (оставшиеся темы членов на начало недели / недели до сессии), закрытия по дням за 28 дней, средняя доля тем по блокам курса (подтверждённая диагностикой тема считается за 1), до 5 самых трудных тем (попыток на решённую задачу, только темы, где решения отправляли хотя бы трое). Ни id, ни логинов, ни имён, ни строк по студентам, ни рейтингов, ни числа отстающих. Если членов меньше 5, итогов нет вовсе (`tooSmall`): в маленькой группе они указывают на конкретных людей. Неизвестная группа или группа без членов курса — `404`.
- **Студент** видит только своё: темп, статус (в том числе «не успеваешь»), прогноз и свою линию закрытых тем по дням — без чужих данных, медиан и рейтингов. Блок есть, только если студент — участник и это курс его сессии.
- **Преподаватель** видит всё с именами: таблицу, флаги, линию каждого члена, сравнение групп.

### Работа на паре

Аналитика для преподавателя о том, как группа работала на паре; студенты её не видят. После пары преподаватель вводит её окно (время по Москве, фронтенд шлёт ISO-8601 со смещением, хранится UTC) и группу (`PairWork`, таблицы `pairs` и `pair_results`). Пара считается фиксированным числом запросов на всю группу; баллы, присутствие и медиана сохраняются и сами не пересчитываются, активность считается на лету.

- **Окно** — `startsAt`..`endsAt` включительно, конец позже начала, не длиннее 6 часов. **Курс** выбирает преподаватель; `GET /api/admin/pairs/course?group=` подсказывает курс сессии большинства участников группы (как в «Аналитике прогресса»), при равенстве — курс, где у группы больше уроков.
- **Кто в паре** — студенты группы с `session_participant = 1`; остальных в паре нет вовсе.
- **Баллы** — задачи курса, у которых первая принятая и не отменённая отправка студента (за всё время) попала в окно и которые сейчас засчитаны (`successful_task_credit`). Вес — сложность задачи (без сложности — 1), у hard-задачи ×10. В `tasks` — сколько задач каждой сложности и сколько hard.
- **Был на паре** — в окне начат урок этого курса, есть отправка или сообщение помощнику (от студента) в уроке этого курса.
- **Активность** — `activeMinutes` = 5 × число 5-минутных отрезков окна (от его начала), в которых есть отправка или сообщение студента помощнику в этом курсе; `submissions` / `failed` — отправки этого курса в окне и непринятые из них; `chatQuestions` — сообщения студента помощнику в уроках курса в окне.
- **Hard-студент** — hard mode в этом курсе действует на момент расчёта (как `hardModeActive`) или в окне засчитана hard-задача; в медиану не входит.
- **Медиана — ориентир «темп относительно группы»** — по сохранённым результатам курса из всех групп, строки «был» и не hard: предыдущая календарная неделя (пн–вс по Москве) относительно начала пары, если в ней ≥ 15 строк (`WEEK`, `medianWeek` — её понедельник); иначе последняя более ранняя неделя с ≥ 15 строками за 12 недель назад (`WEEK`); иначе медиана обычных пришедших студентов этой же пары (`PAIR`); никого — `NONE`. Текущая неделя в свою медиану не входит. `percent` = баллы / медиана × 100 (нет медианы или она 0 — `null`).
- **Пересчёт** (`POST /api/admin/pairs/{id}/recalculate`) — по тем же студентам заново баллы, присутствие, hard и медиана.
- **Журнал** (`GET /api/admin/pairs/journal?group=&language=`) — пары группы по курсу от старых к новым и строка на студента (текущие участники группы и все, у кого есть результат в её парах): ячейка на пару `{attended, points, percent, activeMinutes}` или `null` (студента в паре не было) и `pairs` — на скольких парах был.
- Удаление студента удаляет его результаты; удаление пары — её строки. Неизвестная группа — `404 GROUP_NOT_FOUND`, неизвестная пара — `404 PAIR_NOT_FOUND`.

### К доске

Тест у доски (`BoardTests`, виды заданий и разбор строк — `BoardItems`; таблица `board_tests`, миграции V26, V28): преподаватель вызывает студента со своего ноутбука, студент входит на компьютере аудитории (проектор) и проходит короткий тест; оценку ставит преподаватель. Всё время — UTC ISO-8601.

- **Вызов** — `POST /api/admin/board/call` `{userId, language, kinds}` создаёт `CALLED` на 5 минут; прежние неначатые вызовы этого студента отменяются, вызовы других остаются. Студент видит вызов в `GET /api/board/current` (`{call: {id, calledAt, expiresAt, kinds, durationSeconds}, test}`: активный вызов и идущий тест) и начинает `POST /api/board/tests/{id}/start` — только свой вызов, только пока он активен (повторный старт идущего теста возвращает его же). Истёкший вызов — `EXPIRED`. Преподаватель может всё: `cancel` (вызов или идущий тест; сданный тест только удаляется), `recall` (новый вызов того же студента с теми же видами заданий), `extend` `{seconds: 1..1800}` (вызов — в том числе истёкший — или идущий тест), `finish` (завершить идущий тест сейчас), `DELETE`.
- **Виды заданий** выбирает преподаватель при вызове — любое непустое подмножество (`kinds`; нет поля — все три; пустой список или неизвестный вид — `400 INVALID_KINDS`). Хранятся в `board_tests.kinds` в каноническом порядке, в нём же идут задания теста:

  | вид | в интерфейсе | минуты | вес | тема | сложность банка (по порядку) |
  |---|---|---|---|---|---|
  | `parsons` | «Собери программу» | 2 | 1 | давняя | 2, 1, 3 |
  | `fix` | «Исправь ошибку» | 2 | 2 | недавняя | 2, 1, 3 |
  | `code` | «Напиши код» | 3 | 3 | недавняя | 1, 2, 3 |

  Время теста — сумма минут выбранных видов (все три — 7 минут), `board_tests.duration_seconds`; `endsAt` = старт + это время.
- **Задания** выбираются при старте и сохраняются в тесте (`items_json`); hard-студент получает такой же тест (только `mode='NORMAL'`). Кандидаты — активные задачи курса без ввода (не `IO_BEHAVIOR`); в теме — сначала банк (`CURATED`), затем нерешённая история (`curated:<slug>:`; задача не из банка — история сама по себе), затем сложность в порядке вида, затем предпочтение вида (ниже), среди равных — случайно. Задания одного теста никогда не повторяют задачу или историю. Выбор по очереди: `code`, `fix`, `parsons`. Нет задачи для вида — `400 NO_BOARD_TASK` с названием задания.
  - **Недавние темы** — пройденные практикой (первая итерация; по времени последней принятой отправки той итерации), самая свежая первой; затем подтверждённые диагностикой (с конца курса); затем курс с начала (в первых темах может не быть задач банка с эталоном и неверными решениями для `fix`). **Давние** — пройденные практикой больше 14 дней назад (порядок случайный), затем остальные пройденные и подтверждённые (случайно), затем темы остальных заданий этого теста, затем курс с начала.
  - `code` — первая недавняя тема с кандидатом; короткая задача раньше (эталон добавляет к заготовке ≤ 10 значимых строк; эталон неизвестен — тоже короткая).
  - `fix` — нужны `reference_code` и `wrong_json`. Ошибка — неверное решение банка с наименьшим построчным отличием от эталона (не больше 2 изменённых строк; 1 строка раньше): сравниваются значимые строки (без пустых и строк-комментариев) без пробелов по краям, в Python отступ значим. Тема — первая пройденная или подтверждённая с кандидатом; если выбран и `code` — сначала другие такие темы, затем тема `code` (с другой историей); затем курс с начала. Студент видит программу с ошибкой (`program`), описание ошибки — только преподаватель (`bugDescription`).
  - `parsons` — нужен `reference_code`. Подходит, если в заготовке ровно одна строка-заглушка (`# Напиши решение здесь` / `// Напиши решение здесь`), а эталон — заготовка, где эта строка заменена одним блоком из 4–12 значимых строк (пустые и строки-комментарии блока выбрасываются). `before`/`after` — строки заготовки до и после заглушки (через `\n`), строки блока сохраняют отступ. Лишняя строка — из неверного решения, которое отличается от эталона ровно одной заменённой строкой блока, причём её текст (без пробелов по краям) не совпадает ни с одной строкой блока; нет такого — лишней строки нет. Задачи с лишней строкой раньше. Тема — первая давняя с кандидатом. Строки перемешиваются один раз при старте (никогда не в порядке решения, если возможен другой порядок) и получают id `l1…lN` в показанном порядке.
- **Таймер** — время теста от старта (`endsAt`). Автосохранение `PUT …/answers` `{code?, fix?, parsons?: [id]}` (только поля выбранных видов, по отдельности; `parsons` — id строк этого задания без повторов; иначе `400 INVALID_ANSWER`) и «Запустить» `POST …/run` `{item: "code"|"fix" (по умолчанию code), code}` (лимиты как у `/api/run`; задание должно быть в тесте, иначе `400 INVALID_ITEM`; для `parsons` запуска нет; запуск пишется в `runs_json` с заданием и сохраняет этот ответ) принимаются до `endsAt` + 15 с, позже — `400 BOARD_TEST_OVER`. Клиент сдаёт тест сам (`POST …/finish` с теми же полями), сервер завершает тест, чьё время + 15 с вышло, с последними сохранёнными ответами — при любом запросе «К доске» и каждые 15 с (`BoardTestFinisher`, `app.board.auto-finish.enabled`). Запоздалый `finish` отвечает `{finished: true}`, ответы не меняет. Начальные ответы: `code` — заготовка, `fix` — программа с ошибкой, `parsons` — `[]`.
- **Проверка** — после завершения, по каждому заданию как попытка урока (тестовые случаи задачи или её проверки, с проверкой конструкций; в «посчитай»-задачах вычисление проверяет синтаксическое дерево — LLM здесь оценивает тест целиком), плюс консольный запуск; **ничего не засчитывается** и отправок не появляется. `code` и `fix` — итоговый код студента; `parsons` — программа `before` + поставленные строки в порядке студента + `after` (через `\n`): верен любой порядок, проходящий проверки; ничего не поставлено — «Программа не собрана». Результат задания — `{kind, passed, output, outcome, console, unavailable}` (+ `program` — собранная программа для `parsons`). Сбой песочницы — `unavailable: true`.
- **Оценка** — балл задания: прошло проверку → 1; иначе вердикт LLM «верно» → 1 (например, логика верна и расходится только формат вывода), «частично верно» → 0.5; иначе 0. Очки = Σ вес × балл, максимум = Σ весов выбранных видов, процент = очки / максимум × 100; оценка: ≥ 90 % → 5, ≥ 75 % → 4, ≥ 50 % → 3, иначе 2. `ruleGrade` — оценка только по проверкам. После LLM оценка пересчитывается с баллами LLM непрошедших заданий → `suggestedGrade` = min(эта оценка, потолок); без LLM — min(`ruleGrade`, потолок). Своей оценки LLM не предлагает. В админском виде — `score: {items: [{kind, weight, score}], points, max, percent}`.
- **Оценка LLM** — после проверки, в фоне (платформенный поток, `llm_calls.purpose = 'REVIEW'`), если LLM включена для курса (собственный флаг LLM студента не нужен — это инструмент преподавателя): по каждому заданию — вид, вес, название и условие; для `parsons` — строки правильной программы (с пометкой лишней) и собранная студентом программа; для `fix` — программа с ошибкой и описание ошибки; итоговый код `fix`/`code`; результат проверки; последние ≤ 10 запусков (с заданием), оценка по проверкам → `{summary, items: [{item: parsons|fix|code, verdict: «верно» | «частично верно» | «неверно», explanation}], questions: [1–2 вопроса]}` по-русски, подробно; к оформлению вывода LLM не придирается: если программа печатает правильные значения, а проверка не прошла только из-за формы вывода (пробелы, переводы строк, регистр, знаки, пояснительные слова, разделитель), — «верно» с пометкой в пояснении (кроме «Исправь ошибку», где сама ошибка в формате вывода); `questions` — вопросы, которые преподаватель задаст студенту вслух о его коде; `studentComment` — черновик комментария для студента (1–3 предложения на «ты», без оценки и баллов, ≤ 500 символов): у преподавателя он заполняет поле комментария, пока оценка не выставлена; студент видит только сохранённый преподавателем комментарий. Код и ответы студента — данные, не инструкции (как в проверке «посчитай»). Без LLM или при ошибке — `assessment = {status: "UNAVAILABLE", error}`, преподаватель оценивает сам; `POST …/assess` — оценить заново. Вид оценки: `{status: PENDING|DONE|UNAVAILABLE, summary, items, questions, studentComment, error}`.
- **Потолок по темпу** — статус прогноза к сессии на момент старта (`ProgressAnalytics`): `ON_TRACK`, `DONE`, нет даты сессии или не участник курса — без потолка; `BORDERLINE` — не выше 4; `BEHIND` — не выше 3.
- **Итог** — `PATCH /api/admin/board/tests/{id}` `{finalGrade: "2".."5" | null, comment: ≤ 500 | null, reportVisible: true | false}` (меняются только присланные поля, в любой момент; `reportVisible` — «Показать студенту разбор», по умолчанию `true`, в админском виде теста). Студент в `GET /api/board/grades?language=` видит только тесты с итоговой оценкой: `{id, date (московская), grade, comment, report}`; `report` — `null`, если преподаватель скрыл разбор, иначе по каждому заданию `{kind, title, statement, language, answer, verdict, passed, check, extraUsed}`: свой ответ (для `parsons` — собранная программа), вердикт как в баллах (прошло проверку или «верно» по LLM → «верно», «частично верно», иначе «неверно»), сообщение проверки как на уроке (открытый пример — ожидалось/получилось, скрытый — только номер теста), использована ли лишняя строка (`parsons`, иначе `null`). Эталона, порядка решения, описания ошибки, баллов, предложенной оценки и пояснений LLM в разборе нет: сюжеты банка ещё могут выпасть студенту и одногруппникам. Во время теста студент видит только `{id, status, startedAt, endsAt, now, durationSeconds, items, answers}`: `parsons` — `{title, statement, language, before, after, lines: [{id, text}], extraLines: 0|1}`, `fix` — `{…, program}`, `code` — `{…, starterCode}` — без порядка решения, пометки лишней строки, эталона, описания ошибки, задач банка, проверок, оценок и оценки LLM; после сдачи — ничего.
- **Преподавателю** — сводка теста с `kinds` и `durationSeconds`; полный вид (`GET /api/admin/board/tests/{id}`): задания с `taskId`, `externalKey`, `skillCode`, `skillTitle`, `difficulty` и полными данными (`parsons` — `before`, `after`, `lines`, `solution` — id в порядке эталона, `extraLineId` | null, `reference`; `fix` — `program`, `bugDescription`, `reference`; `code` — заготовка), ответы, результаты, `score`, запуски (с `item`), темп и потолок, оценки, оценка LLM с вопросами.
- **Кого вызвать** (`GET /api/admin/board?group=&language=`): у студента группы — «на месте» (активность в курсе за 60 минут или открытый урок), дата последнего теста, число сданных, последняя итоговая оценка. Подсказка — среди участников сессии без активного вызова: сначала присутствующие, затем давно не отвечавшие (никогда — первыми), случайно из трёх самых давних; не меняется между опросами, пока нет новых вызовов. `active` — вызовы и идущие тесты, недавние (2 часа) и неоценённые сданные.
- **Журнал** — `GET /api/admin/board/journal?group=&language=`: тесты группы (новые сверху) и у студента итоговые оценки сданных тестов от старых к новым (`null` — ещё не оценён).
- Удаление студента удаляет его тесты. Неизвестный тест — `404 BOARD_TEST_NOT_FOUND` (чужой тест для студента — тоже).
- `tasks.reference_code` — программа банка (эталон), `tasks.wrong_json` — неверные решения банка `[{description, source}]` (каждое не проходит проверки задачи): `Verify.java` и `import_bank.py` переносят `reference` и `wrong` из банка; для уже залитых задач — `tools/curated_python/backfill_reference.py BANK_JSON DB` (одна транзакция, по `external_key`, ставит оба столбца и печатает счётчики по каждому, больше ничего не меняет).

### SQLite и транзакции

База работает в режиме WAL (`journal_mode=WAL`, рядом с файлом появляются `-wal` и `-shm` — это часть базы, их нельзя удалять отдельно), с `busy_timeout=15000` и транзакциями `IMMEDIATE`. Настройки передаются драйверу в `spring.datasource.hikari.data-source-properties`.

Правило: внешние вызовы — LLM, Piston, любые HTTP — никогда не выполняются внутри транзакции БД. `/api/learning/next` и `/api/attempts` не транзакционные целиком: чтение и проверка выполняются отдельными запросами, долгая работа — вне транзакции, а связанные записи (задача и её навыки; отправка решения, зачёт и прогресс) — одной короткой транзакцией. Повторный параллельный `/api/learning/next` того же студента и курса ждёт первый и получает ту же задачу. Это проверяет `TransactionBoundariesTest` на файловой базе.

### Логи

Backend пишет в stdout (его видно через `docker compose logs -f backend`). Формат строки:

```
2026-10-06 16:09:53.838  INFO [f67a39f3] student=ivan#12 ApiController: Generated task 41 accepted for skill=LOOPS difficulty=2
2026-10-06 16:09:54.717  INFO [bffcfdd5] admin=teacher student=ivan#12 ApiController: Lesson 7 of student 12 finished by admin 1
2026-10-06 16:10:23.450  INFO [-] TaskAudit: Re-verifying task 18 'Сумма чисел' (skill=LOOPS, language=JAVA)
```

- `[requestId]` связывает все записи одного запроса — HTTP, LLM, проверку решения; он же возвращается клиенту в заголовке `X-Request-Id`. У фоновой работы — `[-]`.
- `student=логин#id` — студент, к которому относится запись: автор запроса студента, а в запросах админа к `/api/admin/students/{id}/...` — студент, которым управляют (у создания аккаунта — новый студент). Записи потока, читающего ответы Codex App Server, получают контекст запроса, начавшего turn, поэтому ответ и размышления модели тоже помечены студентом.
- `admin=логин` — админ, сделавший запрос.
- Системные записи (старт, миграции, фоновая перепроверка задач, общие настройки курса) идут без `student=`.

Время каждой проверки решения — одна строка `CHECK_TIMING` (без отдельной системы метрик):

```
CHECK_TIMING request=abc123 student=35 task=90 language=PYTHON tests_ms=65 console_queue_ms=3 console_piston_ms=48 console_wait_ms=0 total_ms=120
```

`tests_ms` — скрытые проверки от начала до результата Piston; `console_queue_ms` — от постановки фонового запуска консоли до его старта; `console_piston_ms` — запрос консоли к Piston; `console_wait_ms` — сколько запрос ждал консоль в `join()`; `total_ms` — от получения решения до ответа студенту. Выборка: `docker compose logs backend | grep CHECK_TIMING`.

Найти всё по одному студенту: `docker compose logs backend | grep 'student=ivan#12 '`. Поля также доступны в MDC (`studentId`, `student`, `admin`) для JSON-логирования.

- На каждый API-запрос — строка `GET /api/... -> 200 in 35 ms`.
- На каждое обращение к LLM — начало (назначение `CHAT`/`TASK`/`EXPLANATION`, курс, навык, размер промпта) и итог: длительность, токены (вход, кэш, выход, reasoning), размер ответа или причина ошибки/таймаута. Запуск и падение Codex App Server, создание и возобновление thread тоже логируются.
- Генерация задач: каждая попытка и точная причина, по которой задача отклонена (например, «reference solution failed its own checks» или «statement mentions platform internals»).
- Отправки решений: задача, курс, результат и время проверки.

Переменные:

- `APP_LOG_LEVEL` — уровень логов приложения (`INFO` по умолчанию, `DEBUG` добавляет служебные события Codex).
- Ответ модели и сводка её размышлений: включаются в админке («Настройки LLM → Логирование LLM») отдельно для генерации задач и объяснений и для ответов помощника в чате; по умолчанию — `APP_LLM_LOG_GENERATION=true`, `APP_LLM_LOG_CHAT=false`. Для таких обращений App Server запрашивается с `summary=detailed`; модели Codex отдают не сырой ход мысли, а его сводку, и на простых запросах её может не быть — тогда в логе так и написано.
- `APP_LLM_LOG_CONTENT=true` — дополнительно писать полный текст промптов (и ответов для всех видов работы). В них есть сообщения и код студентов, поэтому включайте только на время отладки.
- `APP_LOG_FILE` — путь к файлу логов в дополнение к stdout, например `/app/data/logs/app.log` (ротация по 20 МБ, 14 файлов).

Все обращения к LLM также сохраняются в таблицу `llm_calls`; по ней строится раздел «Аналитика LLM» в админке.

### Два курса: Java и Python

Курсы независимы: у каждого своя диагностика, навыки (коды Python начинаются с `PY_`), уроки с собственной нумерацией и расписанием итераций, прогресс и отдельный thread учебного помощника со своим промптом. Студент выбирает курс сам и может переключаться в любой момент; ограничений доступа нет. Студенческие endpoint'ы принимают `?language=JAVA|PYTHON` (без параметра — Java, как раньше).

Задачи Python проверяются так: студент пишет `solution.py`, скрытые проверки лежат в `test_solution.py` и определяют `run_checks()`, а фиксированная точка входа `main.py` получает секретный маркер успеха через stdin до импорта решения и печатает его, только если `run_checks()` завершилась без исключений. Поэтому маркер не лежит ни в одном файле, который может прочитать код студента.

`APP_PYTHON_DIAGNOSTIC_SOURCE` указывает на диагностику Python (по умолчанию соседний `../python_initial_diagnostic_mvp.md`, в Docker-образе — `/app/python_initial_diagnostic_mvp.md`). Вопросы импортируются при старте, если вопросов Python в базе ещё нет, поэтому уже работающая база получит курс Python после обновления без ручных шагов.

`APP_DIAGNOSTIC_SOURCE` указывает на исходный Markdown диагностики. По умолчанию это соседний `../java_initial_diagnostic_mvp_v2.md`; приложение импортирует вопросы в пустую БД. Этот файл остаётся источником данных и должен быть доступен при первом запуске.

`PISTON_BASE_URL` задаёт URL собственного Piston. Без него отправка решения возвращает `503`; успешный результат не имитируется.

LLM выключена по умолчанию. Адаптер использует один дочерний процесс `codex --disable shell_tool app-server --listen stdio://`, persistent thread в `student_languages` и последовательные turns одного студента. Образ фиксирует Codex CLI `0.159.3`. Без `APP_LLM_ENABLED=true` и `APP_LLM_STUDENT_RUNTIME_VALIDATED=true` чат остаётся **fail-closed** со статусом `STUDENT_RUNTIME_NOT_VALIDATED`; в текущем явно настроенном развёртывании `course.rmzn.net` оба условия прошли проверку sandbox и LLM включена.

Причина: `readOnly` sandbox разрешает чтение, поэтому сам по себе не защищает `auth.json`. Entrypoint копирует управляемый приложением [профиль `student-tutor`](codex-config.toml) в persistent `CODEX_HOME/config.toml`, не затрагивая `auth.json`. Профиль запрещает `:root` и `/app/codex-home`, разрешает только `:minimal` на чтение и отключает сеть. App Server запрашивает этот профиль в `thread/start` и `turn/start`, а `initialize` включает `capabilities.experimentalApi=true`. Перед установкой `APP_LLM_STUDENT_RUNTIME_VALIDATED=true` для нового Linux runtime оператор обязан доказать, что студентский turn не может прочитать `CODEX_HOME/auth.json` и пути вне sandbox. Эта проверка выполнена для текущего `course.rmzn.net`; в другом окружении её нужно повторить. До этого флага вопросы студентов в App Server не передаются.

Модель по умолчанию — `CODEX_MODEL=gpt-6-luna` (для отдельных видов работы — `CODEX_MODEL_CHAT`/`_TASK`/`_EXPLANATION`), уровень размышлений — `CODEX_REASONING_EFFORT=medium`. Уровень передаётся в каждый `turn/start`, включая продолжение существующего диалога. `CODEX_APP_SERVER_COMMAND` позволяет указать другой путь к CLI, но должен запускать App Server с transport `stdio://`; не убирайте `--disable shell_tool` без отдельной проверки безопасности.

### Авторизация Codex и смена аккаунта

Для включённого deployment остановите backend и на том же хосте (либо внутри контейнера с тем же persistent `CODEX_HOME`) выполните вручную:

```sh
codex logout
codex login --device-auth
codex login status
```

Device code нужно подтвердить под нужным ChatGPT-аккаунтом. `codex login status` подтверждает режим авторизации, но не личность аккаунта. В `.env` доступны `APP_LLM_ENABLED`, `APP_LLM_STUDENT_RUNTIME_VALIDATED`, `CODEX_MODEL=gpt-6-luna` и `CODEX_ACCOUNT_NAMESPACE`. Первые два значения остаются `false` по умолчанию. `APP_LLM_STUDENT_RUNTIME_VALIDATED=true` допустим только после проверки на целевом Linux, что студентский turn не может прочитать `CODEX_HOME/auth.json` или пути вне sandbox. Токены, `auth.json` и другие файлы авторизации не выводить и не добавлять в Git.

Для Docker `CODEX_HOME` должен переживать пересоздание контейнера и быть одинаковым для ручного входа и backend:

```yaml
services:
  backend:
    environment:
      CODEX_HOME: /app/codex-home
    volumes:
      - ./codex-home:/app/codex-home
```

Это пример локального запуска; `codex-home` содержит секреты и исключается из Git. Скрипта смены аккаунта в репозитории нет: переключение выполняется вручную указанными командами. Persistent thread нужен для `thread/resume`, поэтому `codex exec --ephemeral` здесь не подходит.

На `course.rmzn.net` пользовательская авторизация используется через этот явный opt-in путь с persistent `codex-home`; при переносе на другой сервер нужно повторить проверку sandbox до включения student runtime. Официальные команды: [OpenAI Codex CLI reference](https://developers.openai.com/codex/cli/reference).

## Осознанные границы первого среза

Есть девять seed-задач и объяснение для `BASIC_CODE_READING` («Вывод в консоль»). Студент дописывает `Solution.main(String[] args)` и использует `System.out.print/println`; скрытый harness запускает `main`, захватывает stdout, восстанавливает `System.out` и сравнивает точный вывод. Старые задачи на предсказание вывода деактивируются при импорте: их идентификаторы, попытки и зачёты остаются в базе, но активный урок их пропускает. Их достаточно для трёх итераций первого навыка при настроенном Piston. Диагностика определяет начальный блок; semantic prerequisite graph в исходных материалах не задан, поэтому `prerequisite_code` пока пустой и готов для заполнения авторами курса. Backend держит студента на одном навыке, пока итерация из трёх задач в уроке не закончена; затем берёт запланированные повторения (итерации 2 и 3), затем новые навыки строго по порядку курса. Внутри итерации задачи идут по сложности 1 → 2 → 3 (`tasks.difficulty`); если в банке нет задачи нужной ступени, при доступной LLM она генерируется, иначе берётся ближайшая по сложности. Объяснения, сгенерированные старой версией промпта (`explanations.prompt_version` < `EXPLANATION_PROMPT_VERSION`), перегенерируются при доступной LLM, а до этого показывается прежний текст.

При отсутствии подходящей задачи backend сначала вызывает `LearningContentGenerator`. Он принимает результат только с названием, условием, starter code, target skill IDs и непустым hidden Java harness, затем сохраняет его в общий банк. Если генератор отключён или не прошёл безопасную проверку App Server, задача не создаётся и API честно отвечает `NO_TASK_AVAILABLE`. При дефолтном fail-closed режиме студентский чат возвращает `503 LLM_UNAVAILABLE` и не запускает App Server; в явно включённом deployment он доступен после проверки sandbox.
