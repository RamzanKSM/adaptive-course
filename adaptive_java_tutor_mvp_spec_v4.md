# MVP: адаптивный учебный сервис по Java с Codex

## 1. Назначение документа

Этот документ фиксирует только те решения по проекту, которые уже были обсуждены.

Он предназначен для передачи агенту-разработчику вместе с отдельным Markdown-файлом, содержащим вопросы диагностического теста.

Агент не должен расширять предметную область, добавлять новые учебные темы, менять модель освоения навыков или придумывать продуктовые возможности, не описанные здесь.

---

# 2. Идея продукта

Нужен учебный сервис для студентов с очень разным начальным уровнем знаний.

Особенность текущей аудитории:

- подавляющее большинство студентов ранее не работали с Java;
- больше половины студентов не умеют программировать ни на каком языке;
- поэтому система должна уметь работать со студентом практически с нулевого уровня;
- нельзя предполагать, что студент уже понимает переменные, выполнение программы, условия, циклы или базовые термины программирования.

Сервис должен:

1. определить исходный уровень студента;
2. понять, с какой темы ему нужно начинать;
3. объяснять материал;
4. выдавать практические задачи подходящего уровня;
5. позволять задавать вопросы LLM по текущей задаче;
6. автоматически проверять решения;
7. постепенно закреплять навыки через повторное решение задач на разных уроках;
8. хранить историю обучения и общения студента с LLM;
9. позволять преподавателю просматривать происходящее.

Главная идея — не генерировать новую задачу каждый раз, а накапливать общий банк задач и повторно использовать уже существующие подходящие задачи.

LLM нужна не только для генерации задач. Она выступает в роли преподавателя внутри учебного процесса.

---

# 3. Текущий scope MVP

В перспективе сервис должен поддерживать как минимум:

- Java;
- Python.

Для каждого языка должна быть своя модель знаний, своя диагностика и свой прогресс студента.

Однако текущий MVP строится на Java.

Python сейчас не реализуется в учебной модели. Для Python позже будет использована отдельная РПД и отдельный набор тем.

Архитектура не должна исходить из предположения, что Java навсегда останется единственным языком.

---

# 4. Пользователи

В MVP есть две стороны:

- преподаватель / администратор;
- студент.

## 4.1. Регистрация студентов

Самостоятельной регистрации студентов не должно быть.

Студента создаёт преподаватель через админскую часть системы.

Студент получает созданный для него аккаунт и входит с выданными учётными данными.

Способ реализации аутентификации в обсуждении не фиксировался.

## 4.2. Преподаватель

Преподаватель должен иметь возможность:

- создавать студентов;
- видеть список студентов;
- включать и отключать взаимодействие конкретного студента с LLM;
- просматривать уроки студента;
- просматривать историю общения студента с LLM;
- просматривать код и попытки решения задач студента.

Расширенная аналитика прогресса по студентам и группам нужна в дальнейшем, но для первого MVP её можно отложить.

Отдельно обсуждалась возможность показывать преподавателю изменение прогресса студента именно за конкретный урок. Это полезное направление, но полноценная аналитическая система сейчас не является основной задачей MVP.

# 6. Первичная диагностика

## 6.1. Цель диагностики

До начала обычного обучения необходимо определить исходный уровень студента.

Диагностика нужна не для выставления общей оценки по Java, а для понимания:

- что студент уже способен понимать;
- какие темы ему неизвестны;
- с какой точки начинать обучение.

Учитывая аудиторию, тест должен начинаться с абсолютного нуля.

Первые вопросы должны проверять даже такие вещи, как:

- может ли студент прочитать простейшую строку Java;
- понимает ли, что такое переменная;
- понимает ли присваивание;
- понимает ли порядок выполнения простых команд.

Далее тест постепенно углубляется в темы текущей Java-модели.

## 6.2. Формат диагностики

Диагностика представляет собой тест с вариантами ответов.

По каждой теме должно быть несколько вопросов.

Один вопрос не должен считаться достаточным подтверждением знания темы, потому что студент может угадать ответ.

Вопросы должны идти от самых простых к более сложным.

Полный конкретный список вопросов хранится в отдельном Markdown-файле и не дублируется в этом документе.

## 6.3. Вариант «Не знаю»

Для каждого диагностического вопроса интерфейс должен дополнительно показывать вариант:

> Не знаю

Этот вариант не нужно хранить внутри данных каждого вопроса.

Он должен добавляться программно ко всем вопросам.

Таким образом, файл с вопросами содержит только содержательные варианты ответа, а UI автоматически добавляет одинаковый вариант `Не знаю`.

Выбор `Не знаю` не даёт положительного подтверждения знания.

## 6.4. LLM во время диагностики

Во время первичной диагностики студент не должен получать помощь от LLM.

Цель теста — определить именно исходный уровень знаний.

## 6.5. Результат диагностики

Диагностика должна определить стартовую точку дальнейшего обучения.

Результаты диагностики должны сохраняться.

При этом прохождение диагностического теста само по себе не означает, что соответствующие практические навыки считаются окончательно освоенными.

Диагностика и дальнейшее практическое закрепление — разные процессы.

# 7. Урок

Основная рабочая сущность учебного процесса — урок.

У студента должна быть кнопка:

- `Начать урок`;
- `Закончить урок`.

## 7.1. Начало урока

При нажатии `Начать урок` начинается новая учебная сессия внутри приложения.

Начало урока НЕ означает создание нового Codex thread.

Система должна использовать постоянный thread соответствующего студента для соответствующего языка.

Для текущего Java MVP это Java-thread студента.

Если thread для этого студента и языка ещё никогда не создавался, он создаётся при первом фактическом использовании Codex.

## 7.2. Содержание урока

Обсуждённый порядок работы:

1. система определяет, над каким навыком студенту нужно работать;
2. студент получает объяснение материала от LLM;
3. студент получает практическую задачу;
4. студент решает задачу;
5. студент может задавать LLM вопросы по текущей задаче;
6. решение проверяется;
7. после успешного решения прогресс соответствующего навыка обновляется;
8. студент может продолжать работу в рамках урока.

LLM не должна работать как простой генератор готовых ответов.

Она должна работать в режиме преподавателя: объяснять, задавать наводящие вопросы и помогать студенту самостоятельно прийти к решению.

Подробный системный prompt преподавателя ещё не был зафиксирован как окончательный текст.

## 7.3. Область чата

Чат во время решения предназначен для вопросов по текущей задаче.

Студент может спрашивать:

- что означает условие;
- почему работает конкретная конструкция;
- почему код не работает;
- попросить подсказку;
- уточнить объяснение, связанное с текущей задачей.

LLM должна видеть контекст текущего учебного процесса через свой постоянный thread.

## 7.4. Завершение урока

`Закончить урок` закрывает урок в нашей системе.

Это НЕ закрывает Codex thread.

Это НЕ создаёт новый thread для следующего занятия.

Это НЕ является моментом, в который впервые пересчитывается прогресс навыков.

Прогресс должен обновляться по факту успешных решений задач.

Закрытие урока фиксирует границу занятия и позволяет сохранить, какие задачи, сообщения и изменения произошли в рамках этого урока.

# 8. Codex как LLM backend

## 8.1. Выбранный вариант

Для взаимодействия с LLM выбран Codex App Server.

Не нужно строить систему вокруг независимых вызовов `codex exec`, в которые на каждом запросе заново передаётся вся история общения.

## 8.2. Постоянный thread

Codex thread принадлежит студенту и языку, а не отдельному уроку.

Концептуально:

```text
Student
├── Java thread
└── Python thread
```

В текущем MVP фактически используется Java thread.

Внутри одного thread проходят разные уроки:

```text
Java thread
├── Lesson 1
├── Lesson 2
├── Lesson 3
└── ...
```

## 8.3. Почему thread долгоживущий

Не нужно каждый раз вручную собирать и отправлять Codex весь контекст всех предыдущих сообщений и уроков.

Продолжение разговора должно происходить в существующем thread.

## 8.4. Compaction / summary

Ручную систему summary истории Codex делать не нужно.

Нужно полагаться на штатную работу Codex с длинным thread и его механизмом compaction.

Нельзя создавать собственную логику, которая периодически сворачивает предыдущие уроки в summary и создаёт новый thread, если для этого нет отдельной необходимости.

## 8.5. Параллельные студенты

У разных студентов разные thread.

Несколько студентов должны иметь возможность работать параллельно.

Внутри одного конкретного student/language thread сообщения должны обрабатываться последовательно, чтобы не создавать конкурирующие одновременные turns одного и того же диалога.

Точное количество параллельных студентов, которое выдержит конкретная конфигурация и аккаунт, заранее не зафиксировано. Это можно проверить нагрузочным тестом при реализации.

---

# 9. Хранение истории чата

Несмотря на то, что историю контекста для LLM хранит Codex thread, наша система также должна сохранять чат в собственной базе.

Причина хранения — не восстановление prompt-контекста Codex.

История нужна преподавателю.

Необходимо иметь возможность увидеть:

- что LLM объясняла студенту;
- какие вопросы студент задавал;
- как LLM отвечала;
- как происходило взаимодействие во время конкретного урока.

Сообщение должно быть связано как минимум:

- со студентом;
- с языком;
- с уроком;
- с ролью отправителя;
- с содержимым;
- со временем сообщения.

Конкретная физическая схема таблиц может быть выбрана при реализации, но данные должны позволять восстановить историю конкретного урока в правильном порядке.

# 10. Отключение LLM

Доступ к LLM должен отключаться на двух уровнях:

- глобально для всего приложения;
- индивидуально для конкретного студента.

Эффективно LLM доступна студенту только тогда, когда включены оба уровня.

Если LLM отключена глобально или для конкретного студента, приложение не должно выполнять обращения к Codex для этого взаимодействия.

Отключение является полным:

- недоступен чат с LLM;
- не генерируются новые объяснения;
- не генерируются новые задачи;
- не выполняются другие обращения к LLM.

В интерфейсе вместо недоступного LLM-взаимодействия можно показывать простую заглушку о том, что LLM отключена преподавателем.

Уже сохранённый в собственной базе контент не требует обращения к LLM. Кэшированные задачи и объяснения остаются обычными данными приложения.

Если для продолжения процесса требуется новый LLM-контент, а LLM отключена, приложение не должно пытаться обходить это ограничение.

# 11. Кэш учебного контента: задачи и объяснения

## 11.1. Общий принцип

LLM не должна генерировать заново один и тот же учебный контент для каждого студента.

В системе должны накапливаться и повторно использоваться как минимум два типа учебного контента:

- практические задачи;
- объяснения учебного материала.

Для обоих действует один принцип:

```text
нужен подходящий материал
        ↓
сначала ищем подходящий материал в собственной базе
        ↓
нашли → используем существующий
        ↓
не нашли → при включённой LLM генерируем через Codex
        ↓
сохраняем результат
        ↓
в дальнейшем переиспользуем
```

Это означает, что стандартное объяснение темы не генерируется заново специально для каждого студента.

Персональное общение начинается уже в чате: студент может задавать вопросы, просить уточнить непонятное место или получить подсказку по текущей задаче.

Если для ответа на конкретный вопрос требуется дополнительное объяснение, LLM может отвечать в рамках постоянного student/language thread. Это не заменяет общий кэш базовых объяснений.

## 11.2. Банк задач

Не нужно генерировать уникальную новую задачу для каждого студента и каждого урока.

В системе должен существовать общий банк задач.

Перед генерацией новой задачи система сначала пытается найти уже существующую задачу, подходящую текущему студенту.

Если подходящая задача есть — используется она.

Если подходящей задачи нет — новая задача может быть сгенерирована через Codex и затем сохранена в общий банк для повторного использования.

Чем больше система используется, тем больше становится банк и тем реже требуется генерация.

## 11.3. Банк объяснений

Для учебных тем / навыков должны сохраняться уже подготовленные объяснения.

Перед тем как просить LLM объяснить студенту новую тему, система должна сначала проверить, существует ли подходящее объяснение в собственной базе.

Если объяснение есть — студент получает его без новой генерации.

Если подходящего объяснения нет и LLM включена — объяснение генерируется через Codex, сохраняется и затем может использоваться для других студентов.

Точная схема классификации нескольких вариантов объяснения одной темы отдельно не определялась.

## 11.4. Связь задачи с навыками

Задача должна быть связана с навыками, которые она проверяет.

Обсуждалось разделение:

- `targetSkills` — навыки, которые задача непосредственно проверяет и по которым успешное решение может давать прогресс;
- `prerequisites` — знания, которые требуются для решения, но не должны автоматически получать прогресс только потому, что использовались внутри задачи.

Пример логики:

```text
Задача проверяет:
- цикл for
- накопление результата

Для решения также требуется:
- переменная
- простой метод

Успешное решение даёт прогресс проверяемым навыкам,
но не обязано давать прогресс всем prerequisite-навыкам.
```

## 11.5. Повторное решение той же задачи

Один и тот же студент не должен получать новый зачёт навыка за многократное повторение одной и той же уже успешно решённой задачи.

Для закрепления нужны разные задачи.

# 12. Выбор следующей задачи

Обсуждённый алгоритм:

1. посмотреть текущую модель знаний студента;
2. определить навык, который ещё не закреплён и над которым нужно работать;
3. учитывать необходимые prerequisites;
4. найти в общем банке задачу, которая проверяет нужный навык;
5. не выбирать задачу, которую этот студент уже успешно решил для текущего закрепления;
6. если подходящей существующей задачи нет — сгенерировать новую через Codex;
7. сохранить новую задачу в общий банк.

Если одновременно доступны несколько подходящих незакреплённых навыков, выбор между ними выполняется случайно.

В случайный выбор должны попадать только навыки, которые уже допустимы для работы с учётом необходимых prerequisites.

# 13. Проверка практических решений

Практические задачи должны проверяться не только субъективной оценкой LLM.

Для Java нужен механизм выполнения кода и автоматической проверки решения.

Обсуждённая общая модель:

```text
Student code
    ↓
Java runner
    ↓
tests
    ↓
success / failure
```

Успешным практическим решением считается решение, которое прошло автоматическую проверку.

LLM может объяснять ошибки и помогать студенту, но не должна быть единственным источником решения вопроса «задача решена или нет».

Конкретная технология sandbox / runner не была зафиксирована и ранее была оставлена на усмотрение реализации.

При этом решение должно безопасно запускать пользовательский Java-код и не позволять неконтролируемому пользовательскому коду нарушать работу сервиса.

Подробная реализация проверки структурных требований к коду отдельно не была окончательно определена.

# 14. Модель освоения навыка

## 14.1. Что влияет на прогресс

Уровень навыка обновляется только по успешным практическим решениям.

Не должны напрямую повышать или понижать навык:

- неправильные попытки;
- количество неправильных попыток;
- количество вопросов в чате;
- использование подсказок;
- время решения.

Эти данные можно хранить для истории и будущей аналитики, но они не являются основанием для изменения прогресса навыка.

## 14.2. Обновление происходит сразу

Прогресс навыка обновляется после успешной проверки решения.

Не нужно ждать нажатия `Закончить урок`.

## 14.3. Одна итерация закрепления

Для завершения одной итерации закрепления студент должен успешно решить:

**3 разные практические задачи по этому навыку.**

Все три задачи относятся к одной итерации.

## 14.4. Полное освоение

Навык не считается освоенным после первых трёх задач.

Для полного освоения требуется:

**3 итерации × 3 разные задачи.**

Итерации должны происходить на разных уроках.

Итого для полного закрепления навыка:

**9 успешных решений**, распределённых по трём отдельным итерациям на разных уроках.

Пример:

```text
FOR_LOOP

Урок A:
  задача 1 ✓
  задача 2 ✓
  задача 3 ✓
→ итерация 1 завершена

Другой урок:
  задача 4 ✓
  задача 5 ✓
  задача 6 ✓
→ итерация 2 завершена

Ещё один урок:
  задача 7 ✓
  задача 8 ✓
  задача 9 ✓
→ итерация 3 завершена

FOR_LOOP → освоен
```

## 14.5. Расписание трёх итераций

Итерации не должны превращаться в девять задач подряд.

Если первая итерация по навыку выполнена на уроке `N`, то:

- итерация 1 выполняется на уроке `N`;
- итерация 2 должна быть выполнена на следующем уроке — `N + 1`;
- итерация 3 должна быть выполнена ещё через два урока после второй итерации — на уроке `N + 3`.

Пример:

```text
Урок 5  → итерация 1
Урок 6  → итерация 2
Урок 7  → без обязательной итерации этого навыка
Урок 8  → итерация 3
```

Такое разнесение используется для лучшего закрепления материала.

Поведение при пропущенном запланированном повторении сейчас находится out of scope.

# 15. Диагностика и освоение — разные вещи

Важно разделять два состояния:

## Диагностика

Отвечает на вопрос:

> С какого места студенту сейчас разумно начать обучение?

## Практическое закрепление

Отвечает на вопрос:

> Подтвердил ли студент навык практическими решениями на нескольких уроках?

Даже хороший результат диагностического теста не заменяет три практические итерации закрепления.

Диагностический тест нужен для выбора стартовой точки, а система освоения навыков продолжает работать во время дальнейших уроков.

# 16. Что сохранять о практической работе

Нужно сохранять историю решения задач, чтобы преподаватель мог позже посмотреть, как проходило обучение.

Для практической попытки нужно иметь возможность восстановить как минимум:

- студента;
- урок;
- задачу;
- отправленный код;
- факт успешного или неуспешного прохождения;
- результат автоматической проверки;
- время попытки.

Точное имя таблицы и формат хранения результата тестов не фиксировались.

# 18. Концептуальные сущности

Это не жёсткая SQL-схема, а перечень сущностей, которые были выделены в обсуждении.

## Admin

Преподаватель / администратор системы.

## Student

Студент, созданный администратором.

Связан с:

- настройкой доступа к LLM;
- диагностикой;
- уроками;
- прогрессом;
- chat history.

## StudentLanguage

Связь студента с языком.

Нужна в общей модели потому, что один и тот же студент в будущем может иметь независимый прогресс по Java и Python.

Здесь хранится связь с соответствующим Codex thread.

## Skill

Учебный навык в рамках конкретного языка.

## StudentSkill

Состояние закрепления конкретного навыка конкретным студентом.

Должно позволять определить:

- сколько задач текущей итерации уже успешно решено;
- сколько итераций завершено;
- освоен ли навык.

## Task

Практическая задача из общего банка.

Связана с языком и навыками.

## Lesson

Конкретный урок студента.

Имеет начало и завершение.

Не является Codex thread.

## ChatMessage

Сообщение студента или LLM в рамках урока.

## Submission

Практическая попытка решения задачи.

Хранит код и результат проверки.

## DiagnosticResult

Результаты первичной диагностики должны сохраняться.

Конкретная форма сущности или таблиц не фиксировалась.

# 21. Что нельзя потерять при реализации

Ключевые продуктовые решения:

1. Студенты сами не регистрируются.
2. Студентов создаёт преподаватель.
3. Текущий MVP строится вокруг Java.
4. Диагностика начинается с абсолютного нуля.
5. На каждый вопрос диагностики UI программно добавляет `Не знаю`.
6. Вопросы диагностики хранятся отдельно от этой спецификации.
7. Диагностика не заменяет практическое закрепление навыка.
8. LLM — преподаватель, а не только генератор задач.
9. Чат привязан к текущей задаче.
10. Один student/language имеет долгоживущий Codex thread.
11. Новый урок не создаёт новый Codex thread.
12. `Закончить урок` не закрывает Codex thread.
13. Не нужно делать собственный manual summary старых Codex-диалогов.
14. Весь чат дополнительно сохраняется в SQLite для преподавателя.
15. Задачи переиспользуются.
16. Новая задача генерируется только когда подходящей в банке нет.
17. Практическое решение проверяется автоматически, а не только LLM.
18. Прогресс обновляется сразу после успешного решения.
19. Ошибки, подсказки и количество попыток не изменяют уровень навыка.
20. Одна итерация = 3 разные успешно решённые задачи.
21. Полное освоение = 3 такие итерации на разных уроках.
22. Повторные итерации должны быть разнесены во времени.
23. Точный spaced-repetition алгоритм пока не определён.
24. Преподаватель может отключить LLM конкретному студенту.
25. LLM можно отключить глобально для всего приложения.
26. При отключённой LLM не выполняются обращения к Codex.
27. Объяснения, как и задачи, кэшируются и переиспользуются; они не генерируются заново для каждого студента.
28. Итерация 2 выполняется на следующем уроке после итерации 1.
29. Итерация 3 выполняется ещё через два урока после итерации 2.
30. При выборе между несколькими допустимыми незакреплёнными навыками используется случайный выбор.
31. Каждая новая сгенерированная практическая задача обязательно генерируется вместе со скрытым Java test harness.
32. Hidden tests хранятся на backend и никогда не отправляются студенту.
33. Расширенная аналитика откладывается после MVP.

# 22. Уточнённые решения и оставшийся out of scope

## 22.1. Повторение навыка

Зафиксировано:

- итерация 1 — урок `N`;
- итерация 2 — следующий урок `N + 1`;
- итерация 3 — урок `N + 3`;
- каждая итерация содержит 3 разные успешно решённые задачи;
- поведение при пропущенном повторении сейчас out of scope.

## 22.2. Выбор между несколькими навыками

Если одновременно подходят несколько незакреплённых навыков, система случайно выбирает один из допустимых вариантов.

Prerequisites при этом продолжают учитываться.

## 22.3. Отключение LLM

LLM имеет:

- глобальный переключатель;
- индивидуальный переключатель для студента.

Если любой из них выключен, обращения к Codex запрещены.

Для недоступного чата / LLM-функции можно использовать простую UI-заглушку.

Кэшированный контент не требует обращения к LLM и остаётся данными приложения.

## 22.4. Sandbox / Java runner

Для MVP выбран **self-hosted Piston**.

Причина выбора: сервис уже решает задачу безопасного запуска недоверенного пользовательского кода и поддерживает Java. В дальнейшем он также подходит для Python, который планируется добавить отдельным направлением.

Приложение не должно самостоятельно реализовывать sandbox на Docker-контейнерах для каждой отправки. Backend взаимодействует с Piston через его API.

Концептуально:

```text
Student code
    ↓
Backend
    ↓
Piston API
    ↓
Java compile / run
    ↓
результат выполнения
    ↓
Backend проверяет результат задачи
```

Piston разворачивается локально на нашем VPS.

Для self-hosted установки допустимо использование требуемого Piston privileged-контейнера.

Piston отвечает именно за изолированный запуск пользовательского кода и resource limits.

Backend приложения отвечает за учебную логику:

- какую задачу выполняет студент;
- какой код относится к конкретной попытке;
- какие проверки нужно выполнить;
- считается ли решение задачи успешным;
- какой прогресс навыков обновить после успешного решения;
- сохранение Submission и результатов проверки.

Интеграцию с Piston нужно скрыть за собственным интерфейсом приложения, например концептуальным `CodeRunner`, чтобы учебная бизнес-логика не зависела напрямую от конкретного execution engine.

Для Java MVP через Piston нужно поддержать как минимум:

- компиляцию Java-кода;
- запуск Java-кода;
- передачу необходимых файлов / тестового harness, если это требуется для проверки задачи;
- получение stdout;
- получение stderr;
- получение exit code / результата выполнения;
- обработку timeout и других ошибок выполнения.

Не нужно использовать публичный Piston API. Используется собственный self-hosted instance.

Формат проверки задачи зафиксирован следующим образом.

При генерации новой практической задачи LLM должна генерировать не только условие задачи, но и скрытую Java-проверку для этой задачи.

Задача и её тест создаются как единый комплект.

Концептуально:

```text
GeneratedTask
├── условие
├── targetSkills
├── prerequisites
├── starter code / ожидаемый контракт решения, если он нужен
└── hidden Java test harness
```

Нельзя сохранять в общий банк новую сгенерированную задачу отдельно от её теста.

Для MVP не требуется обязательное использование JUnit.

Предпочтительный вариант — обычный скрытый Java test harness, например `TestRunner.java`, который компилируется и запускается вместе с кодом студента.

Причина: Piston поддерживает передачу нескольких файлов в одном execution request, поэтому backend может передать одновременно:

```text
StudentSolution.java
TestRunner.java
```

Тестовый файл хранится только на backend и не отправляется студенту на frontend.

Общий flow проверки:

```text
студент отправляет код
        ↓
backend получает hidden test текущей задачи
        ↓
backend формирует multi-file execution request в Piston
        ↓
Piston компилирует student code + test harness
        ↓
test harness запускает проверки
        ↓
backend получает результат
        ↓
все проверки успешны → Submission SUCCESS
иначе → Submission FAILURE
```

Тест должен проверять именно контракт конкретной задачи.

Если задача генерируется через LLM, тест генерируется в той же операции генерации задачи или как обязательная часть одного процесса генерации. Результат генерации считается неполным, если тест отсутствует.

Сами hidden tests студенту не показываются.

Подробный формат протокола между `TestRunner` и backend (например, exit code или структурированный stdout) можно определить при реализации.

## 22.5. System prompt интерактивного LLM-преподавателя

Ниже приведён базовый system prompt для постоянного student/language Codex thread.

```text
Ты — персональный преподаватель программирования для студента.

Сейчас ты обучаешь студента Java.

Большинство студентов этого курса являются абсолютными новичками:
они могут никогда раньше не программировать и могут не знать базовых терминов.
Никогда не предполагай наличие знаний, которых нет в переданном профиле студента.

Твоя задача — помогать студенту самостоятельно понять материал и решить текущую задачу.

ОСНОВНЫЕ ПРАВИЛА

1. Работай как преподаватель, а не как решатель задач.

2. Не выдавай студенту готовое полное решение текущей практической задачи и не пиши за него полный код решения.

3. Если студент не знает, что делать:
   - сначала выясни, какое место ему непонятно;
   - объясни нужную идею простыми словами;
   - задай наводящий вопрос или предложи следующий небольшой шаг.

4. Если студент просит готовый ответ или готовый код, не давай полное решение.
   Помоги ему сделать следующий шаг самостоятельно.

5. Можно использовать небольшие отдельные примеры кода для объяснения концепции,
   но пример не должен фактически являться готовым решением текущей задачи.

6. Если студент прислал свой код:
   - анализируй именно его код;
   - объясняй проблему максимально конкретно;
   - не переписывай всё решение целиком;
   - указывай, в какой части рассуждения или кода находится проблема;
   - по возможности подводи студента к исправлению вопросом или небольшой подсказкой.

7. Если системе передан результат компиляции или автоматических тестов,
   считай его источником истины о том, компилируется ли программа и прошла ли она тесты.
   Не утверждай, что решение прошло проверку, если такого результата от системы нет.

8. Не изменяй и не оценивай численно прогресс навыков студента.
   Прогресс рассчитывает приложение по результатам успешных практических решений.

9. Не решай самостоятельно, какой следующий навык или какую следующую задачу нужно выдать.
   Это выбирает приложение.

10. Основной контекст разговора — текущая учебная тема и текущая задача.
    Отвечай на вопросы студента, связанные с ними.

11. Если для понимания текущей задачи студенту не хватает более базовой концепции,
    объясни эту концепцию настолько, насколько необходимо для продолжения текущей работы.

12. Объясняй простым языком.
    Вводи новые термины только тогда, когда они действительно нужны, и сразу объясняй их.

13. Не перегружай новичка большим количеством информации за один ответ.
    Предпочитай один понятный следующий шаг нескольким страницам теории.

14. Если студент ошибается, не ограничивайся сообщением о том, что ответ неверный.
    Помоги понять причину ошибки.

15. Если студент решил задачу правильно, кратко подтверди это.
    Не объявляй навык освоенным: решение о прогрессе принимает приложение.

КОНТЕКСТ, КОТОРЫЙ ПЕРЕДАЁТ ПРИЛОЖЕНИЕ

Приложение может передавать тебе:

- текущий профиль знаний студента;
- текущую тему / навык;
- стандартное объяснение, которое уже было показано студенту;
- текущую практическую задачу;
- код студента;
- результаты компиляции;
- результаты автоматических тестов;
- информацию о начале или завершении урока.

Стандартное объяснение темы может быть взято приложением из общего кэша.
Не считай, что обязан заново генерировать полное объяснение темы в начале каждого урока.
Если студент задаёт вопрос по уже показанному объяснению, отвечай на конкретный вопрос
и при необходимости переформулируй непонятную часть.

Отвечай студенту на русском языке.
Java-код, названия конструкций Java и общеупотребимые технические термины используй в их обычной форме.

ЦЕЛЬ

Не просто довести студента до зелёных тестов, а помочь ему понять,

```

Этот prompt относится к интерактивному student/language thread.

Генерация новых кэшируемых задач и стандартных объяснений — отдельные LLM-операции и не должна использовать этот prompt как prompt интерактивного преподавателя.

## 22.6. Продвинутая аналитика

Нужна в будущем, но не входит в обязательный объём первого MVP.

# 23. Отдельный файл диагностических вопросов

Конкретные вопросы диагностики должны храниться отдельно от данного документа.

Агенту будут переданы как минимум два файла:

```text
PROJECT_SPEC.md
JAVA_DIAGNOSTIC_QUESTIONS.md
```

`PROJECT_SPEC.md` описывает продукт и правила.

`JAVA_DIAGNOSTIC_QUESTIONS.md` содержит сами диагностические вопросы, варианты ответов, правильные ответы и привязку вопросов к навыкам.

В `JAVA_DIAGNOSTIC_QUESTIONS.md` не нужно вручную добавлять вариант `Не знаю`.

Приложение добавляет его программно к каждому вопросу.
